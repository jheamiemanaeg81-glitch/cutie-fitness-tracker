Notation: |o--< = One to Many | >--< = Many to Many

3NF Logic Thinking 💡

1NF: No repeating groups. Each set is stored as a separate row in SETS.

2NF: `reps` and `weight` are in SETS because they fully depend on set_id.

3NF: `muscle_group` is in EXERCISES because it only depends on exercise_id.

SQL Script 📜

CREATE TABLE USERS (
  id INTEGER PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  role VARCHAR(50)
);

CREATE TABLE EXERCISES (
  id INTEGER PRIMARY KEY,
  exerciseName VARCHAR(50),
  muscleGroup VARCHAR(50)
);

CREATE TABLE WORKOUTS (
  id INTEGER PRIMARY KEY,
  userId INT,
  workoutDate DATE,
  FOREIGN KEY(userId) REFERENCES USERS(id)
);

CREATE TABLE SETS (
  id INTEGER PRIMARY KEY,
  workoutId INT,
  exerciseId INT,
  reps INT,
  weight REAL,
  FOREIGN KEY(workoutId) REFERENCES WORKOUTS(id),
  FOREIGN KEY(exerciseId) REFERENCES EXERCISES(id)
);

📄 System Design Report

1. Scenario

The Cutie Fitness Tracker is a database design project for 3 types of users: Trainer, User, and Teacher.

2. Entities

USERS: id, name, role
EXERCISES: id, exerciseName, muscleGroup
WORKOUTS: id, userId, workoutDate
SETS: id, workoutId, exerciseId, reps, weight

3. Relationships

One-to-Many: One User can have many Workouts
One-to-Many: One Workout can contain many Sets
One-to-Many: One Exercise can be used in many Sets

4. Normalization

1NF: All attributes contain atomic values.
2NF: Reps and weight depend only on set_id.
3NF: Muscle_group depends only on exercise_id.

5. Conclusion

This project demonstrates a 3NF normalized database design.

6. Explanation & 3 User Roles

1. Trainer - Coaching & Demo 💪
Goal: Maintain peak performance
2. User - General Fitness 🎀
Goal: Stay healthy and active
3. Teacher - Stress Relief & Health 🧘
Goal: Improve flexibility
